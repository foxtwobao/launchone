# 官方客户端安装包自动镜像方案

状态：镜像服务、自动同步、原生校验 workflow 和客户端下载流程已实现，待部署及双平台原生验收。本文不代表镜像下载和自动同步已经上线。部署步骤及当前可开放的平台边界见 [镜像部署与运行](installer-mirror-operations.md)。

## 目标与用户体验

让中国用户通过 LaunchOne 下载 Codex / ChatGPT 和 Claude 桌面客户端，无需直接访问海外下载站，也无需管理员手动维护安装包。

用户操作保持不变：未安装时点击“安装”，LaunchOne 识别当前系统、系统版本和机器原生 CPU 架构，获取对应清单并确认兼容后，从自己的下载服务获取官方完整包，校验后进入安装；安装完成并重新检测成功后显示“打开”。下载和安装不要求登录 IDONE。界面只显示下载、校验、安装进度和必要错误，不增加下载源选择、版本列表或镜像设置。

这里的“自动发布”仅指新包保存到服务器并切换安装包清单，不涉及重新构建 LaunchOne、GitHub Release，也不会自动替换用户已安装的 Codex / Claude。LaunchOne 自身的更新继续使用现有 updater 流程。

## 部署方式

```text
LaunchOne 客户端
  ├─ 服务域名 → 服务 Caddy → LaunchOne：鉴权、更新检查、安装包清单
  └─ 下载域名 → 下载 Caddy → LaunchOne：文件下载、断点续传
                                  ↑
                           本地安装包存储目录
                                  ↑
                      自动同步任务 ← 官方稳定下载源
```

两个域名可以使用不同的 Caddy 和网络线路，下载域名走三网优化。文件统一存放并由 LaunchOne 服务读取、返回，Caddy 只反向代理，不挂载包目录、不使用 `file_server`。首期继续使用现有 Node/Express 服务，无需对象存储、CDN、管理后台或额外数据库。

下载 Caddy 只放行 `/downloads/files/` 和现有 `/updates/files/`，其他路径拒绝；服务 Caddy 提供 API，按需要拒绝文件路径。两端都保留原始路径，使用 HTTPS。安装包下载通过流式读取和 HTTP Range 返回，不能把整个文件加载进内存；部署时验证代理超时和大文件下载行为。

## 配置与接口

| 配置项 | 配置位置 | 用途 |
| --- | --- | --- |
| `LAUNCHONE_SERVICE_URL` | 客户端构建配置 | LaunchOne 自己的服务地址，用于配置下发、授权取 Key、更新信息和安装包清单；TokenOne 模型地址和模型名从该服务读取，不作为打包参数 |
| `LAUNCHONE_DOWNLOAD_BASE_URL` | 服务端环境变量，新增 | 构造对外 HTTPS 下载地址；客户端无需编译此域名 |
| `LAUNCHONE_INSTALLER_DIRECTORY` | 服务端环境变量，新增 | 完整安装包根目录，绝对路径 |

同步间隔首期固定为 6 小时，不增加用户设置。Lab、production 分别配置自己的服务域名、下载域名及存储目录；lab 允许两个域名先指向同一台主机。生产配置缺失时拒绝启用镜像，不隐式返回 lab 下载地址。

新增匿名接口：`GET /v1/installers/:app/:platform/:arch`。应用 ID 沿用现有 `codex`、`claude-desktop`；系统支持 `macos`、`windows`；首期 LaunchOne 发行仍以 macOS Universal 和 Windows x64 为范围，协议预留 ARM64 组合不代表已经开放安装。架构明确区分 `aarch64`、`x86_64`。只返回适配器确认兼容的组合，不支持时明确返回不可用，不猜测其他芯片安装包。

清单包含应用 ID、系统、请求架构 `arch`、包内已验证支持的架构 `supportedArchs`、最低系统版本 `minOsVersion`、实际版本和构建号、包格式、文件大小、SHA256、下载 URL。`minOsVersion` 来自包元数据及已核实的官方要求，采用更严格的要求；无法确认时不发布。macOS 使用系统版本，Windows 使用包含 build 的系统版本，按数字分段比较，不按字符串排序。URL 使用配置的下载域名，指向不可变文件，例如 `/downloads/files/claude-desktop/windows/x86_64/<version>/<sha256>/Claude.msix`。官方版本字符串不直接作为未经校验的文件路径。

### 客户端自动选包与兼容性

选包由客户端识别本机条件、服务端适配器映射到已验证文件共同完成，用户无需选择安装文件：

| 本机环境 | 请求的系统和架构 | 可返回的包 |
| --- | --- | --- |
| Intel Mac | `macos/x86_64` | Intel 包，或已验证含 `x86_64` 的 Universal 包 |
| Apple Silicon（M 系列）Mac | `macos/aarch64` | Apple Silicon 包，或已验证含 `arm64` 的 Universal 包 |
| Windows x64 | `windows/x86_64` | 已验证的 x64 包 |
| Windows ARM64 | `windows/aarch64` | 已验证的 ARM64 包 |

客户端查询机器原生架构，不能只用 LaunchOne 的编译目标或当前进程架构。尤其是 M 系列 Mac 通过 Rosetta 运行 Intel 版 LaunchOne 时，仍请求 `aarch64`；Windows 的仿真进程同理。平台 API 返回的 `arm64` 统一映射为接口的 `aarch64`。无法可靠识别或没有对应包时明确提示不可用，首期不自动回退到需要仿真的另一种架构。Universal 包可由两个架构的清单引用同一不可变文件，但必须分别确认其架构支持。

客户端在下载前核对清单的应用、系统、请求架构、`supportedArchs` 和 `minOsVersion`。低于最低系统版本时提示需要升级系统，不开始下载；首期只提供当前稳定版，不自动选择历史兼容版本，保留上一版不代表承诺兼容版本分发。安装前再次核对包内架构及系统要求，不能把签名有效或安装检测成功视为系统兼容。

客户端下载服务可以后续迁移域名，只需修改服务端配置和生成的清单，不需要重新打包。镜像访问不携带 IDONE Token 或 TokenOne Key，跨域重定向也不转发任何鉴权信息。

现有 LaunchOne 更新接口同样可用 `LAUNCHONE_DOWNLOAD_BASE_URL` 构造安装包 URL，但仍保留独立更新清单和更新签名；第三方客户端包不能与 LaunchOne 更新包混用。

## 客户端下载与断点续传

服务端支持 Range 只是前提，客户端必须新增可恢复的下载流程。现有 macOS 下载使用临时目录，中断后文件会被删除，不能直接沿用为断点续传；现有 Windows 流程只打开官方入口，需新增本地下载、校验及调用系统安装器的流程。

1. 下载开始时固定本次清单快照，以应用、系统、原生架构和 SHA256 标识任务，在当前用户私有缓存目录保存 `.part` 文件和清单快照，不使用随调用结束删除的临时目录。同一任务只允许一个写入者，续传偏移以本地文件实际长度为准；网络中断或应用重启后可继续。
2. 服务端以内容 SHA256 生成强 ETag，提供准确的文件大小、`Accept-Ranges` 和 `Content-Range`。客户端有部分文件时发送 `Range: bytes=<已下载长度>-` 与对应的 `If-Range`；只有返回 `206`，且范围起点、总大小和 ETag 与任务一致时才追加。
3. 返回 `200` 表示未执行续传，必须截断旧文件并从头写入，不能追加。收到不一致的 `206` 则停止并丢弃该部分文件；收到 `416` 时，仅当本地长度已等于预期大小才进入完整校验，否则从头重试。下载累计大小不得超过清单声明和客户端上限。
4. 清单在后台发布新版不影响正在下载的任务，不能把新版字节接到旧版部分文件。旧文件返回 `404/410` 或域名迁移导致原地址不可用时，重新获取清单：只有应用、系统、架构、大小和 SHA256 都一致，才可在新 URL 续传；内容变化则重新检查兼容性并新建下载任务。自动重试有次数上限，失败后保留可恢复状态并提示重试。
5. 文件完整后重新计算整个文件的 SHA256，核对大小，并完成应用身份、原生架构、系统要求及官方签名验证，通过后才允许安装。哈希不匹配时删除该文件；安装完成后清理缓存。未完成任务超过 7 天未使用可清理，正在下载或安装的任务不清理；缓存空间不足时明确报错。

续传仅恢复下载，不自动重复执行安装器。LaunchOne 重启后先重新检测安装状态，未安装时由用户点击继续安装；安装取消、失败或需要系统重启时不能提前显示为已安装。

## 自动同步官方版本

由 systemd timer 每 6 小时执行一次同步脚本，首次部署立即执行；同步脚本与服务共用本地存储。下载在后台进行，不占用用户的 HTTP 请求；同一时刻只运行一个同步任务，避免重复下载。现有服务只需读取已发布文件，可保留只读文件系统权限。

每个应用有一个内置下载源适配器，负责系统、架构、官方稳定下载入口、包格式和预期发布者。未来增加应用时新增适配器，不建设通用爬虫或插件市场。

同步流程：

1. 优先读取官方稳定更新清单或固定下载入口，不依赖网页版本文案。可用 ETag、Last-Modified 或官方哈希减少重复下载；这些值只用于判断是否可能变化，不作为安全校验依据。无可靠元数据时允许重新下载并比较 SHA256。
2. 发现候选包后下载到临时目录。仅允许适配器列出的官方 HTTPS 来源和已确认的官方 CDN 重定向；限定超时、大小，拒绝 HTML 错误页和不完整包。
3. 读取包内实际版本、构建号、系统、支持的架构及最低系统版本，核对官方清单中的声明，防止下载入口返回旧包或错误平台；Universal 包分别验证支持的架构。比较版本和构建号，同版本同内容跳过，较旧版本不自动覆盖现行版本。
4. 验证官方签名和预期发布者，计算 SHA256。已有官方哈希时一并比较；自行计算的 SHA256 不能证明发布者身份。
5. 校验通过后，将原始包放入不可变的版本目录，再原子替换该应用、系统和架构组合的现行清单。各组合独立发布，某个组合失败不会阻断其他组合，也不会留下指向未下载完整文件的地址。
6. 记录同步时间、候选版本、成功或失败原因，通过现有服务日志/systemd 状态查看；失败在下轮重试，继续提供上一次校验通过的版本，不清空清单。

失败时保留旧包，首次同步尚未成功则接口返回“暂不可用”，客户端允许重试，不静默跳到用户无法访问的海外站点。服务器重启后直接提供已有包；定时任务补跑，不影响下载服务启动。

至少保留当前版和上一版，旧包退出清单后至少保留 7 天，清理与同步互斥，避免切换清单时删除仍被引用的包；已打开的下载流应能继续完成。版本目录含内容哈希，同版本被官方重新打包时也不会覆盖旧地址。缓存策略采用清单短缓存、版本文件长缓存，避免客户端拿到半更新状态。

## 官网来源与平台差异

跟随的是官网公开稳定下载渠道，不承诺拿到客户端分批灰度推送中的最新版本。官网更新后，通常在下一次检查、下载及校验完成后可用。自动发布只检查安装包来源、签名、完整性、身份、架构和系统要求，不增加逐个上游版本的 TokenOne 兼容白名单或人工放行。TokenOne 配置时检查连接，失败时提供重试和重新连接入口。

| 应用和平台 | 对接方式与边界 |
| --- | --- |
| Codex / ChatGPT macOS | 对接当前官方桌面客户端下载源，不能永久依赖旧 `Codex.dmg`；验证包标识、发布者、架构和系统要求，兼容当前桌面检测逻辑 |
| Claude macOS | 获取官方完整 DMG，沿用应用身份、芯片和系统签名验证 |
| Claude Windows | 优先验证官方完整 MSIX 路径，不能只镜像随后还需要海外下载的 Setup；安装权限、服务、依赖和 Code/Cowork 功能需真机验证 |
| Codex / ChatGPT Windows | 需确认当前官方稳定渠道是否公开完整可安装包及必需依赖；当前微软安装入口不能直接当成离线包。不从第三方抓取 Store 包，不改包；未验证前该组合不宣称支持镜像安装 |

同步时下载完整主包不等于完全离线：WebView2、系统组件、安装器二次下载等都必须在验收中识别。必要依赖仅在有官方可用安装方式且实现验证后纳入镜像；依赖未解决的组合保持不可用，不能把一个联网启动器包装成“已支持”。

## 校验如何落地

Linux 服务端能完成 HTTPS 来源约束、下载完整性、包元数据和哈希检查，但不能假定可直接运行 macOS 的 `codesign` / `spctl` 或 Windows 的原生验证工具。

实施时先验证 Linux 上可用的签名验证工具是否能可靠核对发布者、完整性和信任链；没有可靠方式的包，新增专用 GitHub Actions 校验 workflow，使用对应系统 runner。现有 workflow 仅提供 LaunchOne 打包，不能直接作为第三方安装包校验结果。无需管理员逐版确认，也无需把下载文件放到 GitHub 供用户下载。

远程校验按以下协议实施：

1. 同步任务生成唯一且不可预测的 `requestId`，持久化候选文件的 SHA256、大小、应用、系统、架构、官方 URL、部署环境和截止时间。服务端配置固定仓库、专用 workflow 及受保护 ref，并记录本次预期的 workflow 提交 SHA；这些配置不从候选包或公开请求读取。
2. 同步任务通过带认证的 GitHub API 自动触发 `workflow_dispatch`。关联信息包含 `requestId` 和候选摘要；通过唯一请求标识关联此次运行并记录 run ID，不能选择“最近一次成功运行”。GitHub 凭据只供同步任务使用，按触发、查询运行及读取报告所需的最小仓库权限配置，不交给客户端下载服务，也不传入候选文件下载请求。调用方式参考 [GitHub workflow API](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)。
3. runner 从同一个已确认的官方 URL 获取候选文件，独立执行来源与重定向限制，先核对大小和 SHA256，再执行原生签名、预期发布者、应用身份、架构和系统要求检查。若官方可变入口已换包导致哈希不同，本次失败，由下一轮重新发现候选，不能把另一个包的成功结果用于当前候选。候选包仅用于检查，不执行其中的安装器或应用；校验 workflow 不持有 LaunchOne 签名密钥及业务服务凭据。
4. runner 上传机器可读的校验报告作为该次运行的 artifact，包含请求标识、部署环境、run ID、run attempt、workflow 提交 SHA、候选摘要、读取的元数据及各项校验结果。同步任务从 GitHub API 查询运行，并只从绑定的 run 读取报告。校验仓库、workflow、事件类型、受保护 ref、提交 SHA、run ID/attempt 和成功状态均符合预期，再核对报告与本地任务逐项一致；不能只相信报告自行声明的身份或一个 `success` 字段。接口参考 [workflow run 查询](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run)及 [run artifact 查询](https://docs.github.com/en/rest/actions/artifacts#list-workflow-run-artifacts)。
5. 首期每次请求只接受首次运行 attempt；失败重试生成新 `requestId`，不接受人工 rerun 的结果。报告缺失、重复、超时、来自其他任务或环境、身份不匹配时都不发布；迟到结果不能恢复已过期任务。同步任务取得可信结果后再次核对本地待发布文件 SHA256，才进入原子发布，并保存报告及 run ID 供审计。同步任务重启后可按已保存的 run ID 继续查询，未能可靠关联的任务按失败处理。

远程等待设置明确的总超时和轮询间隔，单个组合失败或 runner 不可用时保留旧版，继续处理其他组合；不降低验证门槛。结果采用服务端主动查询，不新增匿名回调接口。SHA256 用来绑定文件内容，GitHub 认证 API、受信任 workflow 和具体运行记录共同确定校验结果来源。

客户端安装前仍须核对清单大小、SHA256、应用身份和官方签名：macOS 用系统原生签名与安全评估；Windows 用适合 EXE/MSIX 的系统验证及预期发布者检查。不得重签官方包，不绕过系统安装确认。

## 实施顺序与验收

1. **服务端**：增加安装包目录、含兼容性字段的匿名清单、流式文件接口、强 ETag 和下载域名配置；部署两套 Caddy 路由，先在 lab 验证。
2. **自动同步**：实现内置源适配器、定时任务、校验及原子切换；需要远程校验的组合必须先完成专用 workflow、自动触发、任务持久化和报告认证。优先完成 macOS，再逐个验证 Windows 完整包及依赖。只为已验证的组合开放入口。
3. **客户端**：新增机器原生架构识别和系统版本预检，将硬编码下载地址改为读取服务端清单，实现持久化下载任务及断点续传，补充完整性及原生签名检查。Windows 新增本地安装器调用及取消、失败、需重启状态处理；复用安装检测和打开流程。
4. **验收**：在无法直连官方下载域名的 Mac 和 Windows 上，通过下载 Caddy 完成下载安装、重新检测及打开，并覆盖以下场景：

| 验收范围 | 必须验证的行为 |
| --- | --- |
| 自动选包 | Intel Mac、M 系列 Mac、Rosetta 下的 M 系列 Mac、Windows x64/ARM64 及其仿真进程均按机器原生架构请求；Universal 包包含目标架构；缺少对应包时不猜测回退 |
| 系统兼容 | 低于、等于、高于最低系统版本；低于要求时不下载；清单缺失兼容性字段或与包内要求不符时拒绝安装 |
| 下载恢复 | 网络中断及 LaunchOne 重启后续传；`206` 范围或 ETag 错误、服务端忽略 Range 返回 `200`、`416`、旧文件 `404/410`、域名迁移及清单换版均不拼接错误内容 |
| 完整性与安装 | 包篡改、错误架构、错误发布者、磁盘不足、安装取消/失败/需重启；完整校验前不运行安装器，重新检测成功前不显示“打开” |
| 远程校验 | 正常自动发布；官方入口换包、错误仓库/workflow/ref/提交/run/attempt、任务或环境不匹配、重复/迟到报告、超时、runner 不可用及同步任务重启均按协议处理，失败保留旧版 |
| 发布与清理 | 同步失败、发布时已有下载、旧版本保留期及清理；已有流可完成，未完成下载丢失旧文件时可重新获取清单恢复 |

上线时同步任务应能无人值守运行；日常无需人工下载、上传或切换版本。官方入口结构变化、签名身份变化或缺少完整包时需修复适配器，不能以自动化为由跳过验证。

本方案仅覆盖首次安装和再次下载安装包，不接管 Codex / Claude 自身的应用内更新；也不自动升级用户已安装的应用。
