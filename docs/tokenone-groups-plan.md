# TokenOne 分组接入方案

状态：计划于 2026-11-08 开始实施。本文件只记录方案，不包含已实施功能。

## 目标

LaunchOne 用户可以使用其 TokenOne 账号当前有权使用的分组。默认登录即用 AUTO；需要时，用户可在应用卡片中为 Codex 或 Claude 单独选择分组。不给用户增加管理 composite 组、模型路由或应用授权的复杂设置。

这里的“所有分组”是 TokenOne 针对当前用户实际返回、允许该用户使用的分组，不是实例中全部分组，也不承诺平台 AUTO 当前没有覆盖的分组自动进入 AUTO。

## 用户体验

- 首次授权默认 AUTO，不增加必选步骤或单独设置页。
- TokenOne 模式卡片显示一个分组选择器：`自动（AUTO）` 和 TokenOne 返回的可用分组。
- Codex 和 Claude 分别保存所选分组；同一用户重启 LaunchOne 后选择不变。
- 当前模式为官方订阅时隐藏或禁用 TokenOne 分组选择。
- 切换分组后只更新对应应用的个人 Key；连接验证成功后保存选择，并沿用现有“确认重新打开”提示。
- 失败时保留原分组和原配置，显示可理解的错误；不自动换组，也不因额度、模型不存在而重试其他组。
- TokenOne 权限后来撤销时，不悄悄改发其他组的 Key；下次刷新分组列表时提示重新选择。

## 方案选择

采用“默认 AUTO + 可选单组”的混合方案。

AUTO 是最少操作的默认值，使用 TokenOne 原生 AUTO 行为与路由配置。手动单组选择补足 AUTO 配置列表之外、但用户本人获准使用的分组。默认不提供多选分组、优先级编辑、跨组重试开关或自建 composite，避免把运维路由责任转给终端用户。

不继续由 LaunchOne 固定创建 composite 分组。Composite 内容及其渠道组合由应用管理员控制，不能代表每位用户自己的完整授权范围。

## 服务端与 Reseller 改动

### Reseller 应用授权

保留现有“应用固定分组”语义，CreativeOne 等现有调用方不变。为 LaunchOne 增加明确的用户选组模式，不能把 `default_group_id` 设为 AUTO，也不能把空分组解释为授权全部分组。

LaunchOne 授权时服务端应：

1. 基于已验证的 IDONE issuer/subject 找到 TokenOne 本人账号。
2. 读取 New API 原生的 `/api/user/self/groups`，只把该用户获准的普通分组和 AUTO 能力返回给桌面端；不得返回管理员 token 或其他用户数据。
3. 用户选择具体组时，在服务端再次查询并校验当前权限，再以该组创建或更新该应用专属的个人 Key。
4. 用户选择 AUTO 时，只在上游原生支持并经过验收的情况下创建 `group="auto"` Key。`auto_groups` 未设置时继承平台默认列表；LaunchOne 不伪造或快照管理员全局 AUTO 列表。
5. `keys:ensure` 只读取当前已授权选择的 Key，不得因普通刷新而创建替换 Key。改变选择需走单独、可审计的显式操作，并保持授权本人、配额和 Key 生命周期约束。
6. 对每个 `app_id + identity + instance` 记录当前选组模式/分组及对应 Key。禁止一个应用读取另一个应用的 Key。模型 Key 保持用户所有，继续受用户权限、额度和分组计费约束。

### 必须先确认的 New API 语义

- AUTO token 在缺少显式 `auto_groups` 时，是否继承全局 AUTO 候选列表，以及 `cross_group_retry=false` 时同一模型是否会按候选组逐一查找可用渠道。
- AUTO 候选组是否在每次请求时按当前用户权限过滤；不得把管理员全局 AUTO 列表当作授予该用户访问所有组。
- 单组 token 是否仅允许该用户当前可用的组，及用户权限变更后的运行时拒绝行为。
- 组名为 `auto` 的创建、更新、Key 校验和实际路由都需在受支持 New API 接口上验收。
- `/api/user/self/groups` 当前返回的组元信息结构及其 AUTO 项，在 Reseller 新增过滤时按契约解析，不能只按组名猜测。

若 AUTO 任一关键语义无法证明，先实现和验收“用户选单组”，AUTO 留待平台确认后开放，不将未验证能力作为默认上线条件。

## 接口建议

沿用现有 LaunchOne 服务到 Reseller 的服务端凭证及最小授权，不把 Reseller 凭证放入桌面应用。

- 新增 `groups:read` scope 或为 LaunchOne 专用的受限授权接口返回用户分组；只授予读取当前授权用户可见分组的能力。
- 授权/Key ensure 响应包含 `selection_mode`、`selected_group`、Key 和权限版本/更新时间；不返回多余用户资料。
- 增加独立的显式选组操作：输入只能是 `auto` 或来自最新用户分组查询的组名；服务端重新鉴权、验证、更新专用 Key，响应仅返回本人新 Key 与生效分组。
- 固定默认组的既有应用接口与数据库行为保持兼容。可为 applications 增加受约束的 selection policy（固定组/用户选组），迁移默认值必须是 fixed，禁止把老数据迁成可选组。
- 对同一用户并发选组使用事务/版本检查，避免旧响应覆盖较新的选择；操作记录 app、用户绑定、旧组/新组、结果，不记录 Key 明文、ID Token 或 access token。

具体 endpoint 名称及数据迁移在检查 Reseller 现有版本和 API 契约后确定；这是实现细节，不在桌面前端做数据库或 New API 直连。

## LaunchOne 桌面改动

- bridge 增加读取本人可用分组及显式选择分组调用。
- 卡片增加简洁原生 select/菜单；显示友好名称，内部传稳定组名。
- 在成功响应后才更新 Key、当前组和本地选择；失败时保持旧状态。
- 更新本机安全凭据时使用现有 Key 存储设施，不写日志、不放入 URL、配置明文或渲染层持久存储。
- Codex / Claude 各自独立，后续新适配器继承可选组能力，不在每个 UI 组件重复实现。
- 不因切组改动 Codex 身份、项目清单、SSH 项目、问卷状态或 Claude 的无关配置。

## 实施顺序

1. 固定 New API 和 Reseller 当前接口契约；用测试账号只读查询 AUTO 和本人可用组，验证上述 AUTO 行为。
2. Reseller 先新增隔离测试：固定组兼容、可用组筛选、AUTO 创建/继承、越权组拒绝、Key 归属、并发选组、额度和禁用状态。
3. 按项目规定运行 Reseller 所需的 SQLite、MySQL、PostgreSQL 数据库测试矩阵；若迁移应用表，对旧版本升级和重复迁移进行验证。
4. 实现 Reseller 用户选组 API，旧固定组应用回归不变。
5. 实现 LaunchOne 分组 selector、按应用记忆选择和安全更新 Key；覆盖服务错误、权限撤销、取消、切回订阅和重启场景。
6. 在 lab 测试账号依次验证 AUTO、一个获准组、一个未获准组拒绝、模型调用和工具调用；记录 AUTO 实际可路由范围及余额影响。
7. 完成 macOS / Windows 桌面验收后再打包发布。

## 验收标准

- 新用户登录后不用选组即可通过 AUTO 使用应用。
- 用户可从本人可用组列表选单组，手动输入未授权组名无效。
- 每个桌面应用分组选择独立；重启后仍正确显示和生效。
- 切换成功后 Key 与所选组匹配，失败不丢原 Key/组；不得误用其他应用 Key。
- 只通过实际 TokenOne 权限及额度控制访问，不扩权、不改变平台计费策略。
- 不修改原账号、项目、SSH、问卷状态或其他应用配置。
- 原生客户端在 AUTO 与手选模式都完成实际文本、流式及工具调用。
- 现有固定分组应用及存量授权维持既有行为。

## 明日开始前的边界

只修改 LaunchOne 与 Reseller 约定的源码/配置。New API 源码及生产环境不在本方案修改范围内。Lab 变更仅在用户明确授权的 Lab 服务中进行；先测试和展示具体变更，生产更新另行授权。
